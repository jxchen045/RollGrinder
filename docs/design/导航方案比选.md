# 导航方案比选：从"弹窗切页"到常驻导航

> 起因：实测中发现切换页面要**先弹出一个浮层**再点格子。用鼠标操作时这一步既慢又突兀。
> 本文先把现状量化，再调研主流数控系统的做法，最后给三套可选方案与综合评分。
>
> **本文只做选型，不含实现。** 选定之后再动代码。

---

## 一、先把问题定准：不是"到不了"，是"看不见"

翻代码之后，结论和第一直觉不太一样。**直达能力其实已经有了**：

| 现有通路 | 代码位置 | 到目标页需要几步 |
|---|---|---|
| `Ctrl+1` … `Ctrl+7` 直接切区域 | `ShellWindow.xaml.cs:84-93` | **1 步** |
| `F8`（导航槽，主页时）→ 点格子 | `ShellViewModel.cs:588` | 2 步 |
| 左上角 `☰ RGX` → 点格子 | `ShellWindow.xaml:45-47` | 2 步 |

也就是说，键盘用户**早就能一键切页**，只是**没有任何地方告诉他这件事**——
序号 `1`–`7` 只印在区域菜单的格子里（`AreaMenuItemViewModel.ShortcutText`），
而你得先把菜单打开才看得见它。这是个典型的"可发现性"漏洞：
**唯一说明快捷键的地方，正是快捷键本该让你绕过的地方。**

所以实测中"不友好"的感受，拆开其实是三件事：

1. **可发现性为零**——不打开菜单就不知道有 `Ctrl+n`，于是只能走鼠标两步路。
2. **鼠标行程长**——`☰` 在左上角（约 `x≈20,y≈10..66`），格子在屏幕正中（1100 px 宽的浮层）。
   一次切页要横跨大半块 1920×1080 的屏，再点一个 355×136 的格子。
3. **模态遮挡**——浮层是带 `#B3101418` 蒙版的模态层，页面内容被压暗并 `IsEnabled=false`
   （`ShellWindow.xaml:237`）。**正在磨削时想换页看一眼记录，监控画面会被盖住。**
   这一条在磨削现场比前两条更值得在意。

### 1.1 一个意外发现：现行弹窗其实偏离了我们自己的对标

`导航规范.md` 第二节写得很清楚，导航模型是刻意对齐 SINUMERIK Operate 的：

> Operate 用 `MENU SELECT` 把软键条**临时变成区域菜单**（加工/参数/程序/诊断/调试），
> 区域之间是**平的** → 本软件的**区域菜单**同理。

但 Operate 的 `MENU SELECT` 是让**底部软键条原地换一套标签**，加工画面**照常显示在上面**，
既不变暗也不失效。我们实现成了屏幕中央 1100 px 的**模态浮层**。
换句话说：**现在这个弹窗不是"太像 Operate"，恰恰是"没做到像 Operate"。**
这个认识会直接影响下面的方案排序。

### 1.2 顺带记一处文档漂移

`导航规范.md` 通篇写"**六格**区域菜单"，但 `ShellViewModel.AreaOrder` 现在是 **7 个**
（加了"设置"）。改导航时一并订正。

## 二、调研：主流数控/磨床 HMI 怎么换页

按"换一级画面要做什么动作"归类，业界其实只有四种模式。

### 模式 ①　软键条就地变身（Siemens SINUMERIK Operate）

- 屏幕**底部一排 8 个水平软键** + **右侧一列 8 个竖软键**，对应操作面板上的物理按键。
- `MENU SELECT` 按下后，**底部软键条换成区域清单**（加工 / 参数 / 程序 / 程序管理器 / 诊断 / 调试），
  当前画面**继续显示，不被遮挡**；再按一个软键即进入。
- `RECALL`（◁）只退一级；`MACHINE` 键从任何地方一键回加工画面；`ETC`（»）翻下一组软键。
- **不使用模态弹窗做导航**——弹窗只留给确认与报警应答。

### 模式 ②　物理硬功能键常驻（FANUC 0i / 30i 系列）

- `POS` / `PROG` / `OFFSET SETTING` / `SYSTEM` / `MESSAGE` / `CUSTOM GRAPH` 是**面板上的物理键**，
  永远在那儿，**按一下换一个画面，零步骤**。
- 屏幕底部软键只在该画面**内部**分页。
- 可达性天花板，但**前提是有专用操作面板**——它把"常驻导航"做成了硬件。

### 模式 ③　常驻导航栏（HEIDENHAIN TNC7、Mazak MAZATROL Smooth 系列）

- **TNC7** 把运行模式做成屏幕**左侧一条常驻竖栏**（手动/编辑/程序运行/…），
  右侧工作区用**标签页**切换；这是海德汉从老 TNC 的"右侧竖软键"转向触摸大屏后的新布局。
- **MAZATROL SmoothX / SmoothAi** 是触摸优先设计，功能入口做成**常驻图标标签**（顶部/侧边），
  一点即达，没有中间菜单。
- 共同点：**导航控件永远可见、位置固定、1 次点击到达**，代价是让出一条版面。

### 模式 ④　底部软键 + 固定状态区（Okuma OSP-P300、Mitsubishi M8）

- 本质是模式 ① 的变体：底部软键分组 + 顶部常驻状态/模式区，
  换大类靠软键组切换，同样**不弹模态框**。

### 规范侧的两条硬要求

- **ISA-101**（工业过程自动化 HMI 设计）：画面层级 ≤ 3；**导航控件位置固定**；
  **主画面一步可达**；避免用模态对话框承担常规导航。
- **NAMUR NA 128**：运行中的监控画面**不应被非报警内容遮挡**。

> **调研小结：**
> 七家里**没有一家用模态弹窗做一级画面切换**。
> 主流分两派——**软键条就地变身**（西门子/欧库马/三菱）与**常驻导航栏**（海德汉 TNC7/马扎克）。
> FANUC 那派把常驻导航交给了硬件面板，我们没有专用面板，学不了。

## 三、我们这套系统的约束条件

选方案之前先把"不可动"的列出来，否则评分没有锚。

| 约束 | 内容 | 来源 |
|---|---|---|
| **C1 共屏** | 与 SINUMERIK Operate **共用同一块工控机触摸屏**，操作员在两套界面间来回切 | 项目设定 |
| **C2 最高原则** | 上位机被杀掉这支辊也要磨完；**运行中监控画面的可视性优先级最高** | 项目设定 |
| **C3 版面已定** | 顶栏 76 px + 底部功能条 86 px（8 等宽键），窗口 1920×1080 | `ShellWindow.xaml:41,214` |
| **C4 八键契约** | 前 7 格属页面、第 8 格是导航槽且**物理位置恒定** | `导航规范.md` 四 |
| **C5 戴手套** | 触摸目标不小于约 70 px 高 | `导航规范.md` 6.3 |
| **C6 非触摸场景真实存在** | 调试、工艺编辑、查记录常在办公室用鼠标键盘 | 本次实测 |
| **C7 状态机不该动** | `NavigationModel` 已被 `NavigationTests` 一组守卫锁住，方案应只改**呈现层** | `Navigation/NavigationModel.cs` |

C1 与 C6 是**对着干**的：越像 Operate，鼠标越不顺手；越像桌面软件，和 Operate 的割裂越大。
三套方案的差别，说到底就是这条张力往哪边靠。

## 四、三套方案

### 方案 A　左侧常驻区域栏

> 对标模式 ③（TNC7 / Mazak）。左边让出一条约 180 px 的竖栏，7 个区域常驻，永远 1 击到达。

```
┌──────────────────────────────────────────────────────────┐
│ RGX  辊形编辑           连接 · 权限 · 时钟          76px │
├────────┬─────────────────────────────────────────────────┤
│ 1 自动 │                                                 │
│ 2 工序 │                                                 │
│ 3 辊形◀│              当前页内容                          │
│ 4 手动 │                                                 │
│ 5 记录 │                                                 │
│ 6 诊断 │                                                 │
│ 7 设置 │                                                 │
├────────┴─────────────────────────────────────────────────┤
│ F1  F2  F3  F4  F5  F6  F7 │ F8 返回主页          86px  │
└──────────────────────────────────────────────────────────┘
  180px
```

- 左上角 `☰` 按钮取消（它的职责被整条栏接管）；顶栏腾出的位置放面包屑。
- 每格约 180×130 px，序号 + 页名 + 当前页高亮；离线不可用的格子压暗并就地写明原因。
- 第 8 键保留，但只剩"退一级 / 返回主页 / 返回任务发起页"三种角色，**不再承担打开菜单**。

**优点**

- **1 次点击到达任意区域**，鼠标、触摸都是最短路径——正面命中本次实测的痛点。
- **可发现性满分**：7 个区域及其序号永远印在屏幕上，`Ctrl+n` 不再是隐藏知识。
- **零遮挡**：切页时监控画面一秒都不会被盖住（C2 友好）。
- "我在哪儿"由高亮格直接回答，面包屑变成锦上添花。

**缺点**

- **吃掉 180 px 横向版面（9.4%）**。自动磨削页的实时曲线、记录页的 4 条 ScottPlot 曲线、
  辊形编辑的点表都会变窄——这几页本来就是横向吃紧的。
- **与 Operate 的版面差异最大**。操作员从 Operate 切过来，左边突然多一条栏，
  两套界面的肌肉记忆对不上（C1 受损最重）。
- **改动量最大**：`ShellWindow.xaml` 版面重排 + 7 个页面逐个复核宽度自适应 + 截图/文档重出。
- 7 个入口同时曝光，视觉噪声高于"按需展开"。

---

### 方案 B　软键条就地变身（Operate 原生做法）

> 对标模式 ①。按 `F8`（或顶栏 `☰`）时，底部 8 格**原地**换成 7 个区域键 + 取消，
> **页面照常显示，不变暗、不失效**。再按一下即到。删掉中央浮层。

```
平常：
├──────────────────────────────────────────────────────────┤
│ 保存  另存  新建段  导入  生成  轧辊  下发NC │ 页面菜单  │
└──────────────────────────────────────────────────────────┘

按下 F8 / ☰ 之后（页面内容完全不受影响）：
├──────────────────────────────────────────────────────────┤
│ 自动① 工序② 辊形③ 手动④ 记录⑤ 诊断⑥ 设置⑦ │  取消    │
└──────────────────────────────────────────────────────────┘
```

- 区域键用**明显不同的底色**标出"软键条现在处于菜单态"，避免误按。
- 每格仍写序号，`Ctrl+1…7` 与 `F1…F7` 双通道并存且**常驻可见**。
- `Esc` / 第 8 格 = 取消，回到本页功能键。
- `NavigationModel.IsAreaMenuOpen` 语义原封不动，只换呈现（C7 满足）。

**优点**

- **真正对齐 Operate**，反而是把现行的偏离纠正回来（C1 最优）。
- **零版面代价**，所有页面一个像素都不用改（C3 满足）。
- **零遮挡**：磨削监控全程可见（C2 最优）。
- **改动量最小、回归风险最低**：只改 `FunctionKeys` 的来源 + 删掉 XAML 里的浮层块，
  `NavigationModel` 与其守卫测试完全不动。
- 可盲操：`F8` → `F3` 这种固定按键序列，熟手比看着屏幕点还快。
- 区域名直接印在软键上，**不打开也知道有七个区域**（因为第 8 键写着"页面菜单"）。

**缺点**

- **仍然是 2 步**。鼠标用户从页面中部到底部软键条要走一段（比走到左上角短，但不是零）。
- **"模式态"是认知成本**：同一排键在两种含义间切换，若配色区分做得不够狠，会误按。
- 序号只在菜单态才看得见，`Ctrl+n` 的可发现性只是改善、没有根治。
- 7 个区域 + 取消正好占满 8 格，**将来加第 8 个区域就得翻页**（Operate 用 `ETC »` 解决，我们要另想）。

### 方案 C　顶栏常驻标签条

> 对标模式 ③ 的横向变体（Mazak 顶部标签 / 桌面软件惯例）。
> 顶栏 76 px 之下再加一条 ~56 px 的标签带，7 个区域平铺。

```
┌──────────────────────────────────────────────────────────┐
│ RGX   连接 · 权限 · 时钟 · 状态条                   76px │
├──────────────────────────────────────────────────────────┤
│ 1自动 │2工序│3辊形│▌4手动▐│5记录│6诊断│7设置│      56px │
├──────────────────────────────────────────────────────────┤
│                    当前页内容                             │
├──────────────────────────────────────────────────────────┤
│ F1 … F7 │ F8 返回主页                               86px │
└──────────────────────────────────────────────────────────┘
```

**优点**

- **1 次点击到达**，与方案 A 同级。
- **可发现性满分**，序号常驻。
- **横向版面完全不动**——曲线、点表、记录表格保持现有最大宽度（比方案 A 强的地方）。
- 标签条可以顺带承载面包屑与"已修改 / 运行中·只读"角标，顶栏能瘦下来。
- 改动量中等：只加一行，页面内部不用重排。

**缺点**

- **纵向再吃 56 px**。顶 76 + 标签 56 + 底 86 = **218 px，占 1080 的 20.2%**，
  给内容只剩 862 px——自动磨削页的曲线高度会明显吃紧。
- **触摸目标偏小**：7 格铺 1920 宽是每格约 274 px，但**高度只有 56 px**，
  低于 C5 的约 70 px 要求；加到 70 px 则纵向代价升到 232 px（21.5%）。
- 与 Operate 版面差异同样明显（C1 受损），且"顶部标签页"是很强的桌面软件观感，
  在一块与 Operate 共用的工业屏上略显违和。
- 鼠标从页面中部走到最顶端的距离，比走到底部软键条更远（底边有屏幕边界可以"撞停"，顶边没有）。

## 五、综合评分

### 5.1 评分维度与权重

权重按本项目的实际处境定：现场触摸是**常态**，鼠标是**调试与工艺编辑时的常态**，
两者都不能牺牲；"运行中不遮挡"权重不高只是因为三套方案都做到了，不构成区分度。

| # | 维度 | 权重 | 说明 |
|---|---|---|---|
| D1 | 非触摸（鼠标/键盘）效率 | 20% | 本次实测提出的问题 |
| D2 | 触摸效率 | 15% | 现场主用方式，含戴手套目标尺寸 |
| D3 | 与 Operate 的一致性 | 15% | C1，共屏切换的认知成本 |
| D4 | 可发现性 | 15% | 不看手册能不能发现"怎么换页" |
| D5 | 版面代价 | 15% | C3，让出去的像素 |
| D6 | 改动量与回归风险 | 15% | 含页面重排、文档与守卫测试连带 |
| D7 | 运行中监控不被遮挡 | 5% | C2 |

### 5.2 打分（每项 10 分制）

| 维度 | 权重 | **A 左侧常驻栏** | **B 软键条变身** | **C 顶部标签条** |
|---|---|---|---|---|
| D1 非触摸效率 | 20% | **10** 1 击 + 目标大 + 位置固定 | 8 两击但同带内，或 `F8→Fn` 盲操 | 9 1 击，但鼠标要走到最顶边 |
| D2 触摸效率 | 15% | **9** 180×130 格，戴手套无压力 | 8 两击，但底部软键是手本来就在的位置 | 6 高度仅 56 px，低于戴手套要求 |
| D3 Operate 一致性 | 15% | 4 版面差异最大 | **10** 即 Operate 原生做法 | 5 顶部标签是桌面软件观感 |
| D4 可发现性 | 15% | **10** 7 个入口 + 序号常驻 | 7 需按一下才看见序号 | **10** 同 A |
| D5 版面代价 | 15% | 5 横向 −180 px（9.4%），曲线变窄 | **10** 零代价 | 7 纵向 −56 px，累计占 20% |
| D6 改动量/风险 | 15% | 6 版面重排 + 7 页复核 | **9** 只改软键来源 + 删浮层 | 7 加一行，页面不动 |
| D7 不遮挡 | 5% | **10** | **10** | **10** |
| **加权总分** | | **7.60** | **🏆 8.70** | **7.55** |

算式（供复核）：
- A `= 10×.20 + 9×.15 + 4×.15 + 10×.15 + 5×.15 + 6×.15 + 10×.05 = 7.60`
- B `= 8×.20 + 8×.15 + 10×.15 + 7×.15 + 10×.15 + 9×.15 + 10×.05 = 8.70`
- C `= 9×.20 + 6×.15 + 5×.15 + 10×.15 + 7×.15 + 7×.15 + 10×.05 = 7.55`

### 5.3 敏感性检验：如果更偏向非触摸呢

本次问题是非触摸场景提出来的，所以专门算一版"把 D1 拉到 35%、D2/D3 压到 10%"的极端权重，
看结论会不会翻：

| 方案 | 原权重 | 非触摸优先权重 |
|---|---|---|
| A 左侧常驻栏 | 7.60 | 8.20 |
| **B 软键条变身** | **8.70** | **8.50** |
| C 顶部标签条 | 7.55 | 8.00 |

**即使把"鼠标好不好用"的权重抬到近两倍，B 仍然第一，A 追到第二。**
原因是 B 在版面代价与改动风险两项上是满分，抵掉了它在点击次数上的劣势。
结论对权重不敏感，可以据此决策。

## 六、结论与建议

### 6.1 推荐：方案 B，并强制附带三条补强

单独的 B 只把"遮挡"和"版面"解决了，**并没有把 `Ctrl+n` 的可发现性补到位**。
所以推荐的是 **B + 三条补强**，三条都很小，但正是本次实测痛点的正面解答：

1. **`Ctrl+n` 提示常驻**——在顶栏面包屑旁固定显示当前页序号（如 `③ 辊形编辑`），
   并在页面菜单态的每个软键上印 `Ctrl+n`。让"一键切页"这件事**不用打开任何东西就能发现**。
2. **顶栏 `☰` 保留但改为触发就地变身**，不再弹浮层——
   鼠标用户的入口位置不变，学习成本为零，但按下去不再遮挡画面。
3. **订正文档漂移**——`导航规范.md` 的"六格"改为"七格"，并补一节说明
   "区域菜单 = 软键条变身，不是浮层"。

这样鼠标用户的路径是 `☰ → 软键`（两击，但第二击在屏幕底边、目标 236×62 px），
键盘用户是 `Ctrl+n`（一键，且**现在他知道有这回事**），触摸用户和 Operate 的习惯完全一致。

### 6.2 如果要优先照顾鼠标：选 A，但先解决版面

方案 A 的 8.20（非触摸优先权重）是三者中最高的，**如果后续实际使用中鼠标占比远高于预期，
A 是正确答案**。但选 A 之前必须先回答一个问题：

> 自动磨削页与记录页的曲线，横向少 180 px 之后还够不够用？

这个问题**只有把 WPF 界面真正跑起来才能回答**——而按 `调试就绪评估.md` 的记录，
界面至今只编译过、没在 Windows 上渲染过（开发环境是 Linux）。
所以现在选 A 属于拿没验证过的版面下注。

**折中路线**：先上 B（零版面风险、改动最小），等现场把界面跑起来、量出曲线的实际余量之后，
若鼠标使用确实频繁，再把 A 作为一个**可配置的布局选项**加上去——
届时 `NavigationModel` 不用动，只是多一套 Shell 版面。

### 6.3 不推荐 C

C 的两个硬伤是叠加的：纵向累计吃掉 20% 版面，**同时**触摸目标高度不达标；
想把高度补到 70 px 就得再让 14 px。它唯一强过 A 的地方（不压缩曲线宽度）
被"压缩曲线高度"抵消了，而代价是和 A 一样丢掉 Operate 一致性。

## 七、三套方案的改动落点（供估工）

| 方案 | 要改的文件 | `NavigationModel` | 守卫测试 | 页面 |
